前两篇分别讨论了操作型本体能够带来什么，以及它随之引出的治理问题。这一篇把视线移到机器内部。真正重要的变化，不是模型从小变大，而是软件从描述一个组织，走向在一个被刻意限定的现实模型中行动。

## 本体位于哪一层

数据库首先是存储层；语义层负责稳定指标和定义；知识图谱表达实体与关系；操作型本体还可以加入状态、可执行动作、权限和审计功能。

因此，本体并不是一个装着整个组织的神奇文件格式。它是一层叠在普通数据存储之上的定义、服务与代码。以 Foundry 的思路看，这个结构可以拆成四层：

- **存储层：** 标准数据集保存从源系统抽取的记录。
- **定义层：** 对象类型、链接、动作和函数说明这些记录意味着什么。
- **服务层：** 被索引的对象支持快速查询和受控写回。
- **类型化接口：** SDK 把对象与动作暴露给应用，让开发者不必直接面对裸表。

形式本体的传统远早于今天的 AI 平台。RDF、OWL 和 SPARQL 都试图表达共享概念与关系；医疗领域也长期通过 SNOMED CT、ICD、LOINC、RxNorm，以及 OMOP 等通用数据模型做类似的工作。新的操作性变化，是把这些定义进一步连接到动作。

## 动作层

一个动作类型可以说明它作用于哪个对象、接受哪些输入、允许修改什么、必须满足哪些条件，以及谁有权调用它。审批和决策日志需要明确配置。

配置得当的流程会记录动作造成的修改及其背景。直接写入和外部副作用还需单独检查；动作日志不会自动覆盖所有路径。这样，本体才可能成为操作边界，而不只是地图。

对 AI 而言，这种边界比一句宽泛的“保持安全”更有用。模型可以起草建议，却没有权力直接执行；它可以调用预先定义的动作，却不能临时创造一种新的写入方式；风险更高的动作还可以要求人工批准。

这并不能消除模型错误，但可以缩小错误能够抵达的范围。

## 实体解析必须先发生

对象能够支撑动作之前，系统必须先判断哪些记录指向现实中的同一个对象。不同源系统之间往往没有共享的键。在医疗中，这就是常见的患者匹配或主索引问题。

当可靠标识存在时，可以做确定性匹配；当记录只能靠多个不完善字段比较时，就需要概率匹配。一个典型流程包括：

1. 标准化并清洗源字段。
2. 用分块规则缩小候选比较范围。
3. 对候选匹配进行评分。
4. 自动处理明确案例，把灰区交给人工复核。
5. 当来源冲突时应用幸存者规则。
6. 分配稳定身份，同时保留回到源记录的数据血缘。

不存在完美的阈值。错并会把两个人当成一个，漏并会把一个人拆成两个。不同工作流面对两类错误的代价不同，因此阈值并不只是技术参数。它也编码了组织更愿意承受哪一种错误。

## AI 系统的两条通道

把读取与写入视为两条独立通道之后，这套结构会更容易理解。

**读取通道**检索带有权限和来源血缘的结构化对象。如果相关信息不存在，系统应该暴露这种缺失，而不是补出一个听起来合理的细节。模型仍可能推理错误，但它使用的事实输入可以被检查。

**写入通道**可以把模型限制在预先定义的动作内。校验、权限、批准规则和审计日志必须围绕模型建议明确配置。只有直接写入路径也受到控制时，这种分离才能缩小模型的操作权限。

这里的技术目标是：错误输出不应自动变成不受约束的现实动作。

## 一个临床例子

考虑一个假设的分析问题：在定义好的起始事件之后 180 天内，是否发生过一次符合条件的就诊？

在普通分析流程中，分析师会用 SQL 或其他转换层定义队列、index date、观察窗、删失规则、就诊编码和去重逻辑。这个结果可以很严谨，但它的含义往往仍藏在某个项目专用的代码里。

RAG 加 SQL 的助手可以把自然语言问题转换成查询，却仍要猜测哪个日期是 index，以及什么算作符合条件的记录。相似的字段名可能对应流程中的不同步骤。因此，一个语法完全正确的查询，仍可能返回一个含义错误但看起来合理的数字。

在本体化方法中，时间定义可以挂在可复用的就诊片段对象上。起始事件、随访窗口、删失事件和符合条件的就诊成为明确属性，而不是每次查询时重新拼出的假设。Agent 可以读取这些受治理的对象，并在合适时创建复核建议。任何对源系统的修改仍需另行定义和测试动作路径。

真正的分水岭不是自然语言还是 SQL，而是语义和允许的动作是否存在于可复用、可审查的基础设施中。

## MCP 不等于本体

Function calling 定义调用工具的接口；MCP 提供连接模型、工具和资源的协议；操作型本体则可以定义关联记录的含义，以及流程开放哪些动作。

一种协议可以把模型接到数据库，却不会自动告诉它哪个字段代表临床事件，哪个只是计费产物，哪个 encounter 才建立 index date。连接提供访问，本体提供受治理的解释。

## 成熟度阶梯也是责任阶梯

我们很容易把 AI 系统描述成一条整齐的进阶路线：

- L1：聊天机器人
- L2：检索助手
- L3：工具型 Agent
- L4：带确认环节的工作流 Agent
- L5：本体化操作 Agent

但每向前一步，增加的不只是能力，也是责任。一个系统越从回答走向行动，就越需要稳定定义、狭窄权限、可见的不确定性、复核路径和持久的审计记录。

这也是整个系列的技术结论。本体之所以重要，不是因为它让 AI 听起来知道得更多，而是因为它给了组织一个位置，去决定 AI 可以知道什么、可以建议什么，以及必须在哪里停下。
